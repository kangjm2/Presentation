(약 50초) M-Plane이 왜 생겼는지부터 보겠습니다. CPRI 시대에는 DU와 RU를 같은 회사가 만들었기 때문에, RU 관리는 그 회사 고유의 방식으로 DU가 대신했습니다. 설정 항목도, 경보 형식도, 소프트웨어 업데이트 방법도 회사마다 달랐고, 다른 회사 RU를 붙이려면 연동 개발부터 해야 했습니다. O-RAN 7.2x는 DU와 RU를 서로 다른 회사에서 살 수 있도록 프런트홀을 열었고, 그러려면 데이터를 나르는 C, U 평면과 동기 S 평면뿐 아니라, RU를 관리하는 방법도 표준이 되어야 했습니다. 그게 M-Plane입니다. 목표는 세 가지로 볼 수 있습니다. 어느 O-DU나 SMO든 어느 O-RU를 같은 방식으로 관리하는 상호운용, 사람이 아니라 프로그램이 읽고 쓰는 자동화, 그리고 전파를 내는 장비이기 때문에 관리자가 사라지면 스스로 멈추는 안전입니다. 오늘 볼 YANG, 타이밍, 권한이 각각 이 세 목표에 대응합니다.

(약 55초) 먼저 SMO가 무엇인지 짚고 가겠습니다. SMO는 Service Management and Orchestration의 약자로, O-RAN 망 전체를 관리하고 자동화하는 상위 플랫폼입니다. 비실시간 RIC를 품고 있고, O1 인터페이스로 O-DU와 O-CU를 관리합니다. 기존 망의 EMS와 NMS, 오케스트레이터를 합친 자리라고 보면 됩니다. 구조는 두 가지입니다. 계층형에서는 SMO가 O1으로 O-DU를 관리하고, O-RU는 O-DU만 M-Plane으로 관리합니다. 하이브리드에서는 SMO도 O-RU에 직접 M-Plane으로 연결해, 예를 들어 소프트웨어 관리나 성능 수집을 SMO가 직접 합니다. 어느 쪽이든 역할은 같습니다. 데이터를 가진 O-RU가 NETCONF 서버이고, O-DU와 SMO가 클라이언트입니다. 표준 문서에서는 클라이언트를 O-RU 컨트롤러라고 부릅니다. 메시지는 SSH나 TLS로 암호화된 연결 위에서 오갑니다. 특이한 점은 Call Home입니다. 보통은 클라이언트가 서버에 접속하지만, M-Plane에서는 막 켜진 O-RU가 먼저 컨트롤러에 접속합니다. SSH면 4334, TLS면 4335 포트를 씁니다. 그래서 설치자가 RU 주소를 몰라도 RU가 스스로 관리자를 찾아갑니다. 그리고 클라이언트가 여럿일 수 있기 때문에, 누가 무엇을 바꿀 수 있는지 정하는 권한 제어가 필요해집니다.

(약 50초) 왜 하필 NETCONF와 YANG일까요. 기존 방식과 비교하면 이유가 보입니다. CLI는 사람을 위한 명령어라 벤더마다 문법이 다르고, 여러 줄을 입력하다 중간에 실패하면 반쯤 적용된 상태로 남습니다. SNMP는 오래된 표준이지만 주로 모니터링용이고, 여러 값을 한꺼번에 안전하게 바꾸는 데는 약합니다. NETCONF와 YANG은 IETF가 이 문제를 풀려고 만든 것입니다. YANG으로 데이터의 구조, 타입, 범위를 미리 정의하고, NETCONF로 그 모델에 맞는 메시지를 주고받습니다. 여러 값을 하나의 트랜잭션으로 바꾸고 실패하면 롤백할 수 있고, 알림도 모델로 정의되며, 장비가 어떤 기능을 가졌는지 연결하자마자 자동으로 확인할 수 있습니다. NETCONF는 2006년, YANG은 2010년에 나왔고, Call Home과 접근 제어 NACM까지 갖춰진 뒤 O-RAN이 2019년부터 M-Plane의 언어로 채택했습니다.

YANG ① · 읽는 법

YANG은 데이터의 설계도다 — 값이 아니라 모양을 정한다

module o-ran-uplane-conf {

container user-plane-configuration {

list tx-array-carriers {

key "name";

leaf name { type string; }

leaf center-of-channel-bandwidth {

type uint64; units "Hz"; }

leaf active { type enumeration {

enum INACTIVE; enum SLEEP; enum ACTIVE; } }

leaf state { config false; ... }

} } }

module 하나의 기능 묶음 (o-ran-sync, o-ran-fm …)

container · list 폴더와 표 — list는 key로 행을 구분

leaf · type 값 하나와 그 타입 · 단위 · 허용 범위

config false 장비가 알려 주는 상태 — 쓸 수 없다

rpc · notification 동작 요청과 이벤트도 모델로 정의

feature · deviation 선택 기능, 표준과 다른 점을 장비가 선언

o-ran-uplane-conf에서 발췌 · 단순화 (실제 모델은 더 많은 leaf 포함) · YANG 1.1 RFC 7950

05 / 19

(약 50초) YANG은 데이터의 설계도입니다. 값을 담는 것이 아니라, 값이 어떤 모양이어야 하는지를 정합니다. 왼쪽은 O-RU의 U-Plane 설정 모델에서 송신 캐리어 부분을 단순화한 것입니다. module은 하나의 기능 묶음이고, O-RAN은 동기, 경보, 소프트웨어처럼 기능별로 모듈을 나눕니다. container는 폴더, list는 표라고 생각하면 되고, key로 각 행을 구분합니다. leaf는 값 하나인데, 타입과 단위, 허용 범위가 함께 정의됩니다. 예를 들어 active는 INACTIVE, SLEEP, ACTIVE 세 값만 가질 수 있습니다. config false가 붙은 state는 장비가 알려 주는 상태라서 클라이언트가 쓸 수 없습니다. 이 밖에 rpc로 재시작 같은 동작 요청을, notification으로 이벤트를 정의하고, feature와 deviation으로 장비가 지원하는 선택 기능과 표준과 다른 점을 스스로 선언합니다.

(약 55초) 그럼 YANG 형식으로 메시지를 주고받는 것은 어떤 의미가 있을까요. 왼쪽은 송신 캐리어를 켜는 NETCONF 요청입니다. 태그 이름과 구조가 앞에서 본 YANG 모델과 그대로 일치합니다. 네 가지 의미가 있습니다. 첫째, 계약입니다. 양쪽이 같은 모델을 알기 때문에, 이름이 틀리거나 범위를 벗어난 값은 장비가 오류로 거절하고, 반쯤 적용되는 일이 없습니다. 둘째, 자기 소개입니다. 연결하자마자 hello 메시지와 YANG 라이브러리로 어떤 모듈과 기능을 지원하는지 알려 주고, 필요하면 모델 파일 자체를 받아 갈 수 있습니다. 셋째, 트랜잭션입니다. running에 바로 쓰는 1단계, candidate에 쓰고 commit하는 2단계, 확인이 없으면 자동으로 되돌리는 confirmed-commit 3단계가 있습니다. 넷째, 자동화입니다. 모델에서 코드와 검증기, 시험을 자동으로 만들 수 있어 벤더가 바뀌어도 같은 도구를 씁니다.

(약 55초) 앞에서 본 uplane-conf 모델이 실제로 어떻게 채워지는지 가볍게 보겠습니다. 핵심은 RU가 먼저 보여 준 것 위에 O-DU가 쌓아 만든다는 것입니다. 첫째, O-DU는 RU가 가진 물리 안테나 배열인 tx-arrays와 rx-arrays, RU 안에 미리 정해진 static 끝점, 그리고 인터페이스를 읽습니다. 이것들은 읽기 전용입니다. 둘째, O-DU와 RU 사이의 전송 경로, 즉 VLAN과 MAC 주소를 processing-element로 만듭니다. 셋째, static 끝점과 이름으로 짝을 이루는 low-level 끝점을 만들고, 각각에 eAxC ID를 부여합니다. 이 ID는 RU 안에서 방향별로 유일해야 하고, 겹치면 RU가 거부합니다. 넷째, 캐리어를 만들어 중심 주파수, 대역폭, 이득을 정합니다. 다섯째, low-level link로 끝점, 캐리어, 전송 경로 세 가지를 하나로 묶습니다. 오른쪽 그림이 그 관계입니다. 이렇게 구조가 다 만들어진 뒤에 캐리어를 ACTIVE로 바꾸면 송신이 시작됩니다. 사양은 이 단계들을 한 요청에 묶어도 된다고 하므로, 최종 결과가 모델 규칙을 만족하기만 하면 됩니다.

(약 60초) 두 번째 타이밍 규칙은 감시 워치독입니다. 감시를 구독한 O-DU가 있으면 O-RU는 두 개의 타이머를 돌립니다. 왜 두 개일까요. 생존 확인이 양방향이어야 하기 때문입니다. 하나는 O-DU가 RU의 생존을 아는 용도이고, 다른 하나는 RU가 O-DU의 생존을 아는 용도입니다. 한쪽만 있으면 O-DU가 죽었는데 RU는 모르고 전파를 계속 내는 상황을 막을 수 없습니다. 알림 타이머는 기본 60초로, 그 안에 O-RU가 “나 살아 있다”는 감시 알림을 보냅니다. 감시 타이머는 60초에 여유 10초를 더한 70초로, 그 안에 O-DU가 리셋 RPC를 보내야 합니다. 10초는 알림을 받고 리셋을 돌려보낼 시간 여유입니다. 리셋은 “나도 살아 있다”는 뜻이고, 리셋 RPC로 두 타이머 값을 바꿀 수도 있습니다. 그림처럼 마지막 리셋 이후 70초 동안 리셋이 오지 않으면 감시 실패입니다. 그러면 O-RU는 그 세션을 닫고 다시 Call Home을 시도합니다. 그리고 감시 중인 다른 세션이 하나도 없으면 모든 송신을 멈추고 스스로 리셋합니다. 관리자가 사라진 상태로 전파를 계속 내지 않기 위한 안전장치입니다. 실무에서 자주 걸리는 함정이 있습니다. confirmed-commit의 기본 확인 시간은 600초인데, 이 값이 감시 주기보다 길면 두 타이머가 엉킵니다. 사양은 확인 시간을 감시 주기보다 짧게 두라고 요구합니다.

O-RU가 DHCP로 받은 컨트롤러 주소로 먼저 TCP 접속을 하고, 컨트롤러가 SSH나 TLS로 인증하면서 NACM 그룹이 정해집니다. 둘째, 능력 보고입니다. 컨트롤러가 get으로 물으면 O-RU는 hello, 모듈 목록, module-cap으로 자기가 무엇을 얼마나 할 수 있는지 밝히고, 컨트롤러는 그 범위 안에서 설정을 계획합니다. 셋째, 감시와 경보를 구독합니다. 여기서 워치독이 돌기 시작하고, 경보를 받을 곳이 등록됩니다. 운용 중 고장이 나면 넷째, O-RU가 경보 목록에 올리고 alarm-notif로 알립니다. 다섯째, 조치입니다. 경보에 따라 O-RU가 스스로 캐리어를 끄거나 RF를 차단하고, 컨트롤러는 리셋, 재설정, 현장 출동을 결정합니다. 여섯째, 원인이 사라지면 해제 알림이 옵니다. 리셋을 했다면 O-RU는 다시 Call Home부터 시작하고, 원인은 restart-cause로 확인합니다. 다음 세 장에서 능력 보고, 경보 발생, 경보 이후 동작을 하나씩 보겠습니다.

(약 35초) 정리하겠습니다. M-Plane은 열린 프런트홀에서 어느 회사 RU든 같은 방식으로, 자동으로, 안전하게 관리하기 위해 만들어졌습니다. 그 안에 세 개의 약속이 있습니다. YANG은 무엇을 말할지 정하는 계약이고, 검증과 트랜잭션, 자기 소개를 가능하게 합니다.
