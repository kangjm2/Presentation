(약 20초) 오늘은 O-RAN 프런트홀의 관리 평면, M-Plane과 그 언어인 YANG을 다룹니다. M-Plane이 왜 필요했는지, YANG 모델로 메시지를 주고받는 것이 어떤 의미인지, 그리고 시작 절차와 감시 타이머 같은 타이밍 규칙, 누가 무엇을 바꿀 수 있는지 정하는 권한 제어가 어떻게 하나로 맞물리는지 정리하겠습니다.

02 / 12

(약 50초) M-Plane이 왜 생겼는지부터 보겠습니다. CPRI 시대에는 DU와 RU를 같은 회사가 만들었기 때문에, RU 관리는 그 회사 고유의 방식으로 DU가 대신했습니다. 설정 항목도, 경보 형식도, 소프트웨어 업데이트 방법도 회사마다 달랐고, 다른 회사 RU를 붙이려면 연동 개발부터 해야 했습니다. O-RAN 7.2x는 DU와 RU를 서로 다른 회사에서 살 수 있도록 프런트홀을 열었고, 그러려면 데이터를 나르는 C, U 평면과 동기 S 평면뿐 아니라, RU를 관리하는 방법도 표준이 되어야 했습니다. 그게 M-Plane입니다. 목표는 세 가지로 볼 수 있습니다. 어느 O-DU나 SMO든 어느 O-RU를 같은 방식으로 관리하는 상호운용, 사람이 아니라 프로그램이 읽고 쓰는 자동화, 그리고 전파를 내는 장비이기 때문에 관리자가 사라지면 스스로 멈추는 안전입니다. 오늘 볼 YANG, 타이밍, 권한이 각각 이 세 목표에 대응합니다.

(약 50초) 구조는 두 가지입니다. 계층형에서는 SMO가 O1으로 O-DU를 관리하고, O-RU는 O-DU만 M-Plane으로 관리합니다. 하이브리드에서는 SMO도 O-RU에 직접 M-Plane으로 연결해, 예를 들어 소프트웨어 관리나 성능 수집을 SMO가 직접 합니다. 어느 쪽이든 역할은 같습니다. 데이터를 가진 O-RU가 NETCONF 서버이고, O-DU와 SMO가 클라이언트입니다. 표준 문서에서는 클라이언트를 O-RU 컨트롤러라고 부릅니다. 메시지는 SSH나 TLS로 암호화된 연결 위에서 오갑니다. 특이한 점은 Call Home입니다. 보통은 클라이언트가 서버에 접속하지만, M-Plane에서는 막 켜진 O-RU가 먼저 컨트롤러에 접속합니다. SSH면 4334, TLS면 4335 포트를 씁니다. 그래서 설치자가 RU 주소를 몰라도 RU가 스스로 관리자를 찾아갑니다. 그리고 클라이언트가 여럿일 수 있기 때문에, 누가 무엇을 바꿀 수 있는지 정하는 권한 제어가 필요해집니다.

04 / 12

(약 50초) 왜 하필 NETCONF와 YANG일까요. 기존 방식과 비교하면 이유가 보입니다. CLI는 사람을 위한 명령어라 벤더마다 문법이 다르고, 여러 줄을 입력하다 중간에 실패하면 반쯤 적용된 상태로 남습니다. SNMP는 오래된 표준이지만 주로 모니터링용이고, 여러 값을 한꺼번에 안전하게 바꾸는 데는 약합니다. NETCONF와 YANG은 IETF가 이 문제를 풀려고 만든 것입니다. YANG으로 데이터의 구조, 타입, 범위를 미리 정의하고, NETCONF로 그 모델에 맞는 메시지를 주고받습니다. 여러 값을 하나의 트랜잭션으로 바꾸고 실패하면 롤백할 수 있고, 알림도 모델로 정의되며, 장비가 어떤 기능을 가졌는지 연결하자마자 자동으로 확인할 수 있습니다. NETCONF는 2006년, YANG은 2010년에 나왔고, Call Home과 접근 제어 NACM까지 갖춰진 뒤 O-RAN이 2019년부터 M-Plane의 언어로 채택했습니다.

YANG ① · 읽는 법

YANG은 데이터의 설계도다 — 값이 아니라 모양을 정한다

module o-ran-uplane-conf {

container user-plane-configuration {

list tx-array-carriers {

key "name";

leaf name { type string; }

leaf center-of-channel-bandwidth {

type uint64; units "Hz"; }

leaf active { type enumeration {

enum INACTIVE; enum SLEEP; enum ACTIVE; } }

leaf state { config false; ... }

} } }

module 하나의 기능 묶음 (o-ran-sync, o-ran-fm …)

container · list 폴더와 표 — list는 key로 행을 구분

leaf · type 값 하나와 그 타입 · 단위 · 허용 범위

config false 장비가 알려 주는 상태 — 쓸 수 없다

rpc · notification 동작 요청과 이벤트도 모델로 정의

feature · deviation 선택 기능, 표준과 다른 점을 장비가 선언

o-ran-uplane-conf에서 발췌 · 단순화 (실제 모델은 더 많은 leaf 포함) · YANG 1.1 RFC 7950

05 / 12

(약 50초) YANG은 데이터의 설계도입니다. 값을 담는 것이 아니라, 값이 어떤 모양이어야 하는지를 정합니다. 왼쪽은 O-RU의 U-Plane 설정 모델에서 송신 캐리어 부분을 단순화한 것입니다. module은 하나의 기능 묶음이고, O-RAN은 동기, 경보, 소프트웨어처럼 기능별로 모듈을 나눕니다. container는 폴더, list는 표라고 생각하면 되고, key로 각 행을 구분합니다. leaf는 값 하나인데, 타입과 단위, 허용 범위가 함께 정의됩니다. 예를 들어 active는 INACTIVE, SLEEP, ACTIVE 세 값만 가질 수 있습니다. config false가 붙은 state는 장비가 알려 주는 상태라서 클라이언트가 쓸 수 없습니다. 이 밖에 rpc로 재시작 같은 동작 요청을, notification으로 이벤트를 정의하고, feature와 deviation으로 장비가 지원하는 선택 기능과 표준과 다른 점을 스스로 선언합니다.

(약 55초) 그럼 YANG 형식으로 메시지를 주고받는 것은 어떤 의미가 있을까요. 왼쪽은 송신 캐리어를 켜는 NETCONF 요청입니다. 태그 이름과 구조가 앞에서 본 YANG 모델과 그대로 일치합니다. 네 가지 의미가 있습니다. 첫째, 계약입니다. 양쪽이 같은 모델을 알기 때문에, 이름이 틀리거나 범위를 벗어난 값은 장비가 오류로 거절하고, 반쯤 적용되는 일이 없습니다. 둘째, 자기 소개입니다. 연결하자마자 hello 메시지와 YANG 라이브러리로 어떤 모듈과 기능을 지원하는지 알려 주고, 필요하면 모델 파일 자체를 받아 갈 수 있습니다. 셋째, 트랜잭션입니다. running에 바로 쓰는 1단계, candidate에 쓰고 commit하는 2단계, 확인이 없으면 자동으로 되돌리는 confirmed-commit 3단계가 있습니다. 넷째, 자동화입니다. 모델에서 코드와 검증기, 시험을 자동으로 만들 수 있어 벤더가 바뀌어도 같은 도구를 씁니다.

(약 55초) 이제 타이밍, 즉 시간에 관한 규칙입니다. 먼저 시작 절차입니다. O-RU 전원을 켜면, DHCP로 IP와 VLAN, 그리고 컨트롤러 주소를 받습니다. 동기는 이와 병렬로 시작합니다. 그다음 O-RU가 컨트롤러에 먼저 접속하는 Call Home을 하고, 컨트롤러가 SSH나 TLS로 연결을 맺으며 인증합니다. 연결되면 hello 메시지로 서로 지원 기능을 교환하고, 컨트롤러가 YANG 라이브러리와 스키마를 읽어 이 장비가 어떤 모델을 쓰는지 알아봅니다. 그다음 중요한 단계가 감시 구독입니다. 이때부터 워치독 타이머가 돌기 시작합니다. 이후 소프트웨어 관리, 지연 프로파일 조회, U-Plane 설정을 하고, 경보 구독과 성능 측정을 켠 뒤 캐리어를 활성화합니다. 순서가 정해져 있기 때문에, 어느 회사 컨트롤러든 어느 회사 RU든 같은 흐름으로 올라옵니다. 실제 사양에는 인증서 등록 같은 선택 단계가 더 있습니다.

(약 55초) 두 번째 타이밍 규칙은 감시 워치독입니다. 감시를 구독한 클라이언트가 있으면 O-RU는 두 개의 타이머를 돌립니다. 알림 타이머는 기본 60초로, 그 안에 O-RU가 “나 살아 있다”는 감시 알림을 보냅니다. 감시 타이머는 60초에 여유 10초를 더한 70초로, 그 안에 클라이언트가 리셋 RPC를 보내야 합니다. 리셋은 “나도 살아 있다”는 뜻이고, 리셋 RPC로 두 타이머 값을 바꿀 수도 있습니다. 그림처럼 마지막 리셋 이후 70초 동안 리셋이 오지 않으면 감시 실패입니다. 그러면 O-RU는 그 세션을 닫고 다시 Call Home을 시도합니다. 그리고 감시 중인 다른 세션이 하나도 없으면 모든 송신을 멈추고 스스로 리셋합니다. 관리자가 사라진 상태로 전파를 계속 내지 않기 위한 안전장치입니다. 실무에서 자주 걸리는 함정이 있습니다. confirmed-commit의 기본 확인 시간은 600초인데, 이 값이 감시 주기보다 길면 두 타이머가 엉킵니다. 사양은 확인 시간을 감시 주기보다 짧게 두라고 요구합니다.

(약 50초) 세 번째 타이밍은 말 그대로 시간 동기입니다. 동기 신호 자체는 S-Plane으로 오지만, 그 상태와 설정은 M-Plane의 o-ran-sync YANG 모델로 보고 바꿉니다. 상태는 세 가지입니다. 기준 신호에 잠긴 LOCKED, 기준 신호를 잃었지만 내부 시계로 버티는 HOLDOVER, 그리고 시계가 풀린 FREERUN입니다. HOLDOVER는 장비에 따라 선택 사항입니다. 모델에는 상태 외에도 GNSS, PTP, SyncE 중 무엇을 지원하는지, PTP 도메인이나 허용할 clock class 같은 설정 값, 그리고 상태가 바뀌는 즉시 보내는 알림이 정의되어 있습니다. 중요한 규칙은 FREERUN에서는 캐리어가 비활성 상태만 가질 수 있다는 것입니다. 시계가 맞지 않는 장비가 전파를 내면 다른 셀에 간섭을 주기 때문에, 동기를 잃으면 송신을 멈추고 상태 변경 알림을 보냅니다. 감시 워치독과 같은 철학입니다. 믿을 수 없는 상태면 전파를 멈춥니다.

(약 60초) 이제 권한 제어입니다. 클라이언트가 여럿이니 누가 무엇을 바꿀 수 있는지 정해야 합니다. M-Plane은 IETF의 NETCONF 접근 제어 모델, NACM을 씁니다. 흐름은 이렇습니다. SSH 계정이나 TLS 인증서로 인증하고, 인증서라면 사용자 이름으로 매핑합니다. 사용자는 하나 이상의 그룹에 속하고, 권한은 그룹 권한의 합집합입니다. 그룹마다 모듈별로 읽기 R, 쓰기 W, 실행 X 권한이 정해져 있는데, 실행에는 RPC 호출과 알림 구독이 포함됩니다. 표는 사양의 일부입니다. sudo는 거의 모든 것을 할 수 있고, nms는 관리 시스템, fm-pm은 경보와 성능만, swm은 소프트웨어 관리만 합니다. 하이브리드 구성에서는 O-DU에 hybrid-odu, SMO에 smo를 주는 것을 권장하는데, 표를 보면 캐리어 설정인 uplane-conf는 hybrid-odu만 쓸 수 있고 smo는 읽기만 됩니다. 반대로 동기와 성능 설정은 smo가 씁니다. 역할이 겹치지 않게 나눈 것입니다. carrier 그룹은 여러 사업자가 RU 하나를 나눠 쓸 때 자기 몫만 다루도록 범위를 좁힌 그룹입니다.

(약 55초) 지금까지 본 세 가지가 캐리어 하나를 켜는 요청 안에서 어떻게 만나는지 보겠습니다. 먼저 Call Home 이후 TLS 인증서로 신원을 확인하고, 사용자 이름을 통해 hybrid-odu 그룹 권한을 얻습니다. 다음으로 hello와 YANG 라이브러리로 이 RU가 쓰는 U-Plane 모델의 버전과 기능을 확인합니다. 감시를 구독하면 워치독이 돌기 시작합니다. 이제 캐리어를 ACTIVE로 바꾸는 edit-config를 보냅니다. 권한 검사에서 hybrid-odu는 이 모듈에 쓸 수 있으니 통과합니다. smo 계정이었다면 여기서 거부됩니다. 그다음 YANG 모델로 이름, 타입, 범위를 검증하고 candidate에 반영한 뒤 commit합니다. 하지만 동기 상태가 FREERUN이면 캐리어는 켜지지 않습니다. LOCKED나 HOLDOVER여야 합니다. 켜지면 상태 변경 알림이 오고, 컨트롤러가 확인합니다. 운용 중에 컨트롤러의 리셋이 끊기면 감시 실패로 송신을 멈춥니다. 이렇게 YANG은 무엇을 말할지, 권한은 누가 말할 수 있는지, 타이밍은 언제까지 믿을 수 있는지를 정합니다.

(약 30초) 정리하겠습니다. M-Plane은 열린 프런트홀에서 어느 회사 RU든 같은 방식으로, 자동으로, 안전하게 관리하기 위해 만들어졌습니다. 그 안에 세 개의 약속이 있습니다. YANG은 무엇을 말할지 정하는 계약이고, 검증과 트랜잭션, 자기 소개를 가능하게 합니다. NACM은 누가 말할 수 있는지를 그룹별 모듈 권한으로 정합니다. 타이밍은 시작 순서, 워치독, 동기 상태로 언제까지 믿을 수 있는지 정합니다. 한 줄로 줄이면, 믿을 수 없는 상태가 되면 RU는 스스로 전파를 멈춥니다. 다음 단계로 시험 대상 RU의 YANG 트리, NACM 계정, 워치독 설정을 점검하는 체크리스트를 만들어 보기를 제안드립니다. 감사합니다.
