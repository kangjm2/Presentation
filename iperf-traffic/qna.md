# 예상 질문과 답변: iperf3와 트래픽 시험

슬라이드 순서대로 정리했습니다. 출처는 [README](README.md#출처)에 있습니다.

---

## 02~04. 길 · 패킷 모양 · 트래픽 종류

**Q. 트래픽이 RU나 CU에서 되돌아오는 것 아닌가요?**

아닙니다. RU · DU · CU는 패킷을 나르기만 하고, 되돌려 보내는 것은 UPF 너머의 트래픽 서버입니다. ping은 서버 운영체제가, iperf3는 서버의 iperf3 -s가 응답합니다. 다만 무선 KPI(MCS, BLER, RB, PDCP 처리량 등)는 기지국과 단말에서 생기므로, 기지국에서 재는 것처럼 보일 수 있습니다.

**Q. 서버를 MEC에 두는 것과 인터넷에 두는 것은 무엇이 다른가요?**

인터넷 서버는 유선 구간의 지연과 병목이 더해집니다. TCP는 RTT가 길수록 느려지므로(7쪽), 무선 성능만 보려면 코어나 MEC 가까이에 서버를 두는 것이 좋습니다. 반대로 실제 서비스 체감을 보려면 인터넷 서버도 함께 잽니다.

**Q. GTP-U 머리말도 무선으로 나가나요?**

아닙니다. GTP-U 터널은 기지국과 UPF 사이(N3), DU와 CU 사이(F1-U)의 유선 구간에서만 씁니다. 무선 구간에는 단말 IP 패킷에 PDCP · RLC · MAC 머리말이 붙어서 나갑니다.

## 05. ping

**Q. ping RTT가 들쑥날쑥한 이유는요?**

단말이 상향으로 보내려면 스케줄링 요청 → 그랜트를 거쳐야 하고, 재전송(HARQ)이 생기면 그만큼 늦어집니다. 간격이 길면 DRX나 유휴 상태에서 깨어나는 시간도 들어갑니다. 망 부하와 서버 처리 시간도 섞입니다. 그래서 평균만 보지 말고 분포(중앙값 · 상위 백분위)를 봅니다.

**Q. ping 크기를 키우면 무엇이 달라지나요?**

전송할 데이터가 늘어 무선 전송 시간이 조금 늘고, MTU를 넘으면 분할됩니다. 큰 ping은 경로의 MTU 문제를 찾을 때 씁니다.

## 06~08. TCP · UDP

**Q. TCP 처리량이 UDP보다 낮게 나오는 게 정상인가요?**

대체로 정상입니다. TCP는 ACK를 받으며 창을 키우고, 지연이 흔들리거나 손실 신호가 오면 창을 줄입니다. 그래서 무선이 받아 낼 수 있는 양(UDP)보다 낮게 나옵니다. 차이가 크면 창 크기(-w), RTT, 스트림 수(-P), 서버 · 단말 처리 성능을 확인합니다.

**Q. UDP -b를 무조건 크게 주면 안 되나요?**

받은 속도는 용량 근처에서 멈추지만, 넘친 패킷이 버퍼에 쌓였다 버려지면서 지연이 커지고 단말 · 서버 부하가 늘어납니다. 손실률도 의미 없이 커집니다. 용량보다 조금 높게 주거나, 여러 값으로 나눠 재서 받은 속도가 평평해지는 지점을 찾는 것이 좋습니다.

**Q. 지터는 무엇을 뜻하나요?**

패킷이 도착하는 간격의 흔들림입니다. iperf3는 연속한 두 패킷의 전달 시간 차이를 구해 1/16씩 반영하는 평활 평균으로 계산합니다(RFC 1889 방식). 음성 · 영상 같은 실시간 서비스의 품질과 관련이 큽니다.

## 09~10. iperf3

**Q. DL을 재려면 서버에서 단말로 iperf3 -c를 하면 되지 않나요?**

단말이 공인 주소를 갖고 방화벽이 열려 있으면 가능합니다. 하지만 이동망 단말은 대개 사설 주소 · NAT 뒤에 있어서 바깥에서 연결을 열 수 없습니다. 그래서 단말이 클라이언트로 연결을 열고 -R로 서버가 보내게 합니다.

**Q. sender와 receiver 숫자가 다른 이유는요?**

TCP에서는 보낸 쪽 합계에 아직 도착하지 않았거나 재전송된 데이터가 섞일 수 있고, 끝나는 시점도 조금 다릅니다. UDP에서는 손실된 만큼 receiver가 적습니다. 실제로 전달된 양은 receiver 줄이 정확합니다.

**Q. -P(여러 스트림)를 쓰면 반칙 아닌가요?**

목적에 따라 다릅니다. 무선 구간이 낼 수 있는 최대치를 보려면 단일 TCP 흐름의 창 · RTT 한계를 피하려고 여러 스트림을 씁니다. 실제 앱 하나의 체감을 보려면 -P 1로 잽니다. 보고할 때 스트림 수를 함께 적습니다.

## 11~12. 가상 UE (TUN · netns · curl)

**Q. 왜 네임스페이스(netns)가 꼭 필요한가요?**

UE 주소와 코어가 같은 호스트(또는 같은 대역)에 있으면, 커널이 목적지까지 더 짧은 길을 찾아 TUN을 건너뛰고 패킷을 바로 보낼 수 있습니다. 그러면 트래픽이 가상 무선과 기지국을 지나지 않습니다. 칸을 나누면 칸 안의 앱은 그 UE의 TUN만 보게 되어 반드시 UE 스택을 지납니다. UE가 여러 개일 때 경로가 섞이지 않게 하는 효과도 있습니다.

**Q. TUN과 TAP은 무엇이 다른가요?**

TUN은 IP 패킷(L3)만 주고받는 장치이고, TAP은 이더넷 프레임(L2)을 주고받는 장치입니다. 단말의 사용자 데이터는 IP 패킷(PDU 세션)이므로 가상 UE는 TUN을 씁니다.

**Q. 가상 UE로 잰 처리량을 실단말과 비교해도 되나요?**

그대로는 어렵습니다. 가상 무선(ZMQ · RF 시뮬레이터)은 실제 채널이 아니라서 MCS · BLER · SINR이 실제 값이 아니고, UE 프로그램과 서버의 CPU가 먼저 한계에 닿을 수 있습니다. 기능 · 시나리오 · 부하(동시 UE 수) 시험에 쓰고, 무선 성능은 실단말과 실채널(또는 SDR + 채널 에뮬레이터)로 봅니다.

**Q. curl 대신 iperf3를 써도 되나요?**

됩니다. 칸 안에서 실행하기만 하면 ping · iperf3 · curl 모두 같은 TUN을 지납니다. curl은 실제 HTTP 다운로드라 서비스 체감에 가깝고, iperf3는 TCP/UDP 조건을 세밀하게 정할 수 있습니다.

## 13~15. FTP · 숫자 비교 · 점검표

**Q. FTP와 iperf3 TCP 처리량이 다르면 어느 쪽이 맞나요?**

둘 다 맞고 보는 것이 다릅니다. FTP에는 서버 디스크 · CPU, 파일 크기, 파일마다 새로 여는 연결이 더해집니다. 망 성능은 iperf3로, 실사용 체감은 FTP · 웹으로 봅니다. 차이가 크면 서버 쪽을 먼저 의심합니다.

**Q. DM 로그의 PDCP 처리량과 iperf3 처리량이 몇 % 다르면 정상인가요?**

머리말 차이만 보면 TCP 약 3.5%, UDP 약 2%입니다. 실제 차이는 재전송, TCP의 빈 시간, 시간 창의 차이로 더 커질 수 있습니다. 같은 1초 창으로 맞춰 비교하고, 차이가 머리말 몫보다 훨씬 크면 TCP 동작이나 서버 · 단말 한계를 봅니다.

**Q. 기지국 PM의 처리량(DRB.UEThpDl)이 iperf3보다 높게 나오는 이유는요?**

PM 카운터는 보낼 데이터가 있던 시간 기준으로 평균을 내므로, 데이터가 없던 시간까지 포함한 iperf3 평균보다 높게 나올 수 있습니다. 분모가 다르다는 점을 먼저 확인합니다.
